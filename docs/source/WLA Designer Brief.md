## WITHIN LAB ACADEMY

## WEBSITE + ACADEMY DESIGNER BRIEF

## Production design brief · work from current WLA authorities

This brief tells you what already exists, what governs the design, what to carry forward, what you are expected to produce, where professional judgement is welcome, and what must be ready for development.

WLA is not being designed from a blank page.

The existing public website prototype has already established much of the intended public-site

character. The production Academy, however, must be designed from the current WLA Academy Architecture and the wider WLA visual system — not from the retired Lovable Academy.

## 1. What you are inheriting

You are inheriting:

- an approved public website structure and copy;

- an existing public website prototype showing much of the intended public visual direction;

- an established WLA visual language;

- a frozen Academy Architecture defining the shared learner environment;

- approved WLA mission, privacy and accessibility principles;

- existing mission documents and physical artefacts;

- an established logo concept that requires production refinement rather than reinvention;

- Mission Build Briefs that will define the unique interactions of individual missions.

Your task is to carry this foundation into a coherent, polished and production-ready WLA design system.

## Authority order

## WLA Public Website Master

Controls what exists on the public website: page structure, copy, navigation, CTA logic, mission presentation, Journal structure, FAQ structure and public route roles.

## WLA Academy Architecture

Controls shared Academy behaviour and hierarchy: My Missions, Mission Home, Mission Kit, For Parents, Active Mission, Mission Control, pause/resume, completion, Mission Trail, Mission Board placement and shared mission-status behaviour.

## Individual Mission Build Brief

Controls mission-specific screens, exact screen copy, reveals, response states, branches,

screen ↔ physical handoffs and mission-specific interaction requirements.

## WLA Child Mission / Presentation standards

Control mission-specific physical and child-facing artefacts where relevant.

## This Designer Brief

Controls visual hierarchy, layout, responsive design, shared components, imagery, typography, colour, interaction states, accessibility and design handoff.

If two authorities appear to conflict, do not solve the conflict through visual redesign. Flag it.

## 2. What you are expected to design

The production design scope includes:

- reconcile and complete the approved public website;

- establish the production WLA visual system;

- refine the existing logo for production use;

- define typography, colour, spacing, layout and image application;

- design all required public routes and page states;

- design My Missions;

- design child-profile selection/switching where required;

- design the shared Mission Home;

- design Mission Kit and For Parents;

- design the shared Active Mission shell;

- design Mission Control;

- design Mission Complete and Mission Trail states;

- design reusable components and their interaction states;

- design shared loading, empty, error and unavailable states where relevant;

- apply individual Mission Build Briefs once approved;

- prepare responsive designs for desktop, phone and tablet;

- produce a build-ready developer handoff.

The aim is not to create isolated screens.

The aim is to create one reusable WLA design system capable of supporting a growing mission library.

## 3. Design judgement and continuity

Begin by understanding the WLA foundation already in place and the thinking behind it.

The existing public prototype should be treated as an established expression of that direction, not as a limitation on your professional judgement.

Carry forward what is already working.

Where you see an opportunity for a materially stronger solution, surface it as a considered recommendation rather than changing the established treatment by default.

For any significant departure, show:

- what you are proposing;

- why it would improve the experience;

- how it remains true to WLA.

Review that recommendation with the Founder before implementation.

The expectation is continuity with discernment: respect the strength of what exists, bring a fresh production eye to it, and create space for genuinely better solutions where they are clearly worth pursuing.

## 4. How to use the existing public prototype

The current public website prototype is a validated visual and UX reference, not a production constraint.

You do not need prior Lovable experience.

Use it to understand:

- page rhythm;

- hierarchy;

- spacing;

- visual restraint;

- use of colour;

- editorial character;

- image placement;

- current component behaviour;

- the distinction between expressive content areas and functional actions.

Before materially changing an established page or pattern:

- 1. review the current prototype;

- 2. review the current Website Master alongside it;

- 3. identify what is already working;

- 4. identify anything the current authority explicitly changes;

- 5. surface any materially stronger design approach for Founder review before replacing an established direction.

## The production design should carry forward the prototype’s strengths

## Especially:

- warm cream as the dominant field;

- restrained colour use;

- strong editorial hierarchy;

- generous visual breathing room;

- tactile materiality;

- calm, deliberate section rhythm;

- a coherent five-Lab system;

- selective rather than decorative imagery.

## The production pass should elevate the execution

## Aim for:

- lighter, fresher overall atmosphere;

- more cream and visual air;

- cleaner natural light;

- stronger use of genuine mission artefacts;

- less visual heaviness;

- more resolved typography and spacing;

- complete responsive behaviour;

- complete interaction states;

- stronger distinction between the editorial public website and the quieter functional Academy;

- a reusable system robust enough for future missions.

Do not treat Lovable-specific layout, structure or implementation choices as constraints.

## 5. Retired Academy prototype boundary

The Lovable Academy is retired.

It is not:

- a production Academy reference;

- a screen-flow authority;

- a layout authority;

- a mission-interaction authority;

- a source of current learner journeys.

Do not reproduce its Academy screens, navigation or interaction structure.

Design the production Academy from:

## WLA Academy Architecture + WLA visual system + approved Mission Build Briefs.

## 6. Core design character

WLA should feel:

- warm;

- tactile;

- thoughtful;

- capable;

- structured;

- calm;

- quietly adventurous.

Useful shorthand:

## A beautifully organised field desk before an expedition.

This is a mood reference, not a literal theme.

WLA should not become rustic, costume-like or expedition-branded.

The production expression should feel lighter and fresher: more cream, natural light, paper, material variation and evidence of practice.

Child energy should come through:

- missions;

- objects;

- physical materials;

- visible process;

- changed artefacts;

- evidence that something has been tried.

Parent confidence should come through:

- hierarchy;

- restraint;

- legibility;

- composure;

- clear action.

WLA should not feel like:

- a toy brand;

- a brightly coloured school platform;

- a gamified learning app;

- a generic SaaS dashboard;

- a conventional educational marketplace.

## 7. Colour system

Use the established WLA palette as the production foundation.

## Warm Cream — #F5EFE3

Primary canvas and breathing space.

## Charcoal Brown — #3A2F2A

Primary reading text, headings, navigation and outlines.

## Deep Olive — #5F6A4F

Primary interaction, CTA and active emphasis.

## Soft Sage — #A3B18A

Selective supporting surfaces and calm shifts.

## Clay — #B87C5A

Small accents, markers and restrained detail.

Cream should carry the system.

Sage and clay support rather than compete.

Do not create five separate dominant Lab colour identities. The Labs should remain part of one

coherent WLA system.

## 8. Typography

The approved typographic requirement is:

## editorial warmth + practical clarity.

Use no more than two principal type families:

- a warm, human editorial serif or similarly expressive display face;

- a highly legible humanist sans for body, navigation, interface and instructional content.

The existing public prototype should be inspected to confirm the exact current pairing.

If that pairing already performs well across:

- desktop;

- mobile;

- long-form Journal reading;

- parent-facing copy;

- Academy UI;

- smaller functional labels;

retain it.

If a materially stronger production pairing is recommended, present the case to the Founder before replacing the established typographic direction.

Prioritise:

- clear hierarchy;

- generous but disciplined reading space;

- comfortable long-form measure;

- strong UI legibility;

- consistency between website and Academy.

Avoid:

- novelty type;

- childish display faces;

- handwriting-style navigation or instructions;

- decorative typography that slows comprehension.

## 9. Layout, shape and spatial rhythm

Design should feel spacious without feeling sparse.

Use:

- hierarchy;

- whitespace;

- occasional restrained surface shifts;

- editorial composition;

- purposeful grouping.

Do not default to cards.

Use cards only when they genuinely help organise content or interaction.

Use moderately softened corners.

## Avoid:

- bubbly interface language;

- excessive pill shapes;

- floating-dashboard aesthetics;

- heavy shadows;

- visual dividers between every section.

Where shadows are useful, they should suggest physical materiality:

## paper slightly lifted from a surface, not software floating in space.

Grid, spacing, radius and breakpoint values are production design decisions. Keep them coherent and document them.

## 10. Imagery

## WLA imagery should make the mission world tangible.

Use real or convincingly real mission setups, physical artefacts and visible evidence of action.

Suitable imagery includes:

- Mission Boards;

- trackers;

- cards;

- maps;

- mission sheets;

- notebooks;

- paper;

- rulers;

- tape;

- tools;

- builds;

- test results;

- altered plans;

- marked evidence;

- decision trails;

- objects showing that something has been tried, changed, compared or worked out.

The image world should be:

- object-led;

- naturally lit;

- light and warm;

- predominantly cream or neutral in setting;

- tactile without becoming craft-themed;

- composed but not sterile;

- rich in evidence of process.

## Mission imagery

Once a mission exists, use the mission itself.

For example:

- Six Names should use its actual Mission Board, tracker, cards and case artefacts;

- Mars should use its actual build world and mission materials;

- future missions should increasingly generate their own visual world.

Generic imagery should not substitute for a real mission once genuine mission assets exist.

## Academy-level imagery

Academy imagery may be more conceptual where needed, but it should still belong to the same

WLA world of:

## thinking → trying → noticing → changing → evidence.

## Human presence

WLA’s visual system is people-free.

Do not rely on:

- faces;

- bodies;

- hands;

- classroom stock photography.

The child’s presence is shown through the work they have left behind.

## 11. Logo

## Logo task: finish the existing mark, not redesign it.

Preserve the established concept:

- the two-sided vessel / open-book form;

- rising dotted progression;

- sprout/growth movement;

- olive and clay relationship.

The production refinement should resolve:

- symbol geometry and optical balance;

- symmetry where appropriate;

- the lower centre join;

- small-size legibility;

- upward progression of the dots;

- symbol/wordmark proportion;

- optical spacing of WLA;

- launch-stage hierarchy between WLA and Within Lab Academy;

- clay/olive distinction;

- grayscale performance.

The full Within Lab Academy name should remain legible and meaningful at launch. Do not assume the acronym already has independent recognition.

## Required production family

## Prepare:

- full launch lock-up;

- horizontal header lock-up;

- symbol + WLA;

- symbol-only;

- dedicated small-size/favicon treatment;

- one-colour version.

## Test in:

- desktop website header;

- mobile navigation;

- Academy;

- mission documents;

- favicon;

- social profile;

- grayscale.

Keep “The experiment starts within.” separate from the logo lock-up.

Do not produce alternative logo concepts unless the existing concept genuinely fails after professional refinement.

## 12. System boundary

Design the three WLA layers as related but distinct experiences.

## Public website

Discover → Understand → Choose → Purchase

## My Missions

Access → Open → Return

## WLA Academy

Do → Notice → Complete → Keep growing

The public website may carry more editorial atmosphere.

My Missions should become more functional.

The Active Mission environment should become quieter still.

Do not make all three look like the same dashboard.

## 13. Public website structure

Primary navigation:

## Home | Missions | Labs | Journal | About

Separate functional routes:

My Missions | Try a Free Mission | Reviews | Buy a Gift | Redeem a Gift

Design against the current Website Master rather than creating a new site structure.

## 14. Home

Preserve the approved parent journey and section rhythm.

The page should move naturally through:

## promise → mission glimpse → what missions provide → Labs → family fit → reassurance → origin → action prn

Keep the homepage visually confident and restrained.

Do not add copy simply because a composition feels visually empty.

The design should make the proposition understandable quickly without over-explaining it.

## 15. Missions

The mission catalogue should feel like a collection of experiences, not an online course marketplace.

Use:

- real mission imagery;

- strong titles;

- Lab;

- age;

- duration;

- delivery information;

- clear See Mission action.

Avoid cluttering mission cards with unnecessary commercial information.

As the mission library grows, the cards should remain reusable and coherent.

## 16. Mission Detail

The primary question is:

## Is this a mission we want?

Prioritise:

- mission situation;

- Lab;

- age/duration/delivery;

- concise description;

- materials/preparation where useful;

- Leaves behind;

- price;

- primary purchase action.

Give Leaves behind meaningful visual weight.

Visible evidence is one of WLA’s strongest distinctions.

The page should feel like an invitation into an experience, not a dense ecommerce product page.

## 17. Labs

Preserve the strongest quality already established in the public prototype:

- vertical editorial rhythm;

- restrained markers;

- strong verbs;

- reflective framing;

- coherent WLA character.

The Labs should feel different in purpose without becoming separate visual brands.

## 18. Journal

Journal should feel editorial.

It should not look like:

- Mission cards;

- resource tiles;

- a generic blog grid;

- a secondary product catalogue.

## Use:

- clear featured-story hierarchy;

- strong long-form readability;

- generous breathing room;

- selective imagery;

- restrained article navigation.

The page should visibly slow the pace of the website while remaining recognisably WLA.

## 19. About

## Keep About:

- spacious;

- reflective;

- editorial;

- grounded.

Do not turn the founder story into a conventional corporate biography page.

## 20. FAQ, trust and support routes

Prioritise retrieval and calm readability.

Safety, safeguarding and privacy information should feel:

- credible;

- clear;

- reassuring;

- straightforward.

Do not visually dramatise safeguarding information.

## 21. Reviews, gifts and unresolved flows

Reviews, Buy a Gift and Redeem a Gift are approved routes.

Do not invent detailed commerce or form flows from assumptions.

Where detailed requirements are not yet approved:

- design only the confirmed route/state;

- use the shared WLA form, success, error and confirmation language once requirements are supplied;

- flag missing product decisions.

## 22. My Missions

My Missions is functional.

It should immediately answer:

- What missions do I have?

- What is their status?

- Where do I continue?

The shared statuses are:

- Not started

- In progress

- Complete

The shared actions are:

- Open Mission

- Continue

- View Mission

## Design:

- populated state;

- empty state;

- loading state where required;

- error/unavailable state where required;

- clear mission status;

- strong primary action.

Do not communicate status by colour alone.

My Missions is not a public catalogue and not a generic parent dashboard.

## 23. Child-profile selection and switching

Where more than one child profile exists, the current child must be clear before mission access.

## Design:

- profile selection;

- profile switching;

- active-profile indication;

- associated My Missions state.

The interaction should feel simple and family-oriented, not like social-profile management.

Do not allow child identity treatment to dominate the Academy.

## 24. Shared Academy design

Design one reusable Academy visual system.

The shared journey is:

## My Missions → Mission Home → Active Mission → Mission Complete → Mission Trail → My Missions

The Academy should feel unmistakably WLA but more functional and visually restrained than the public website.

Do not simply place public-site components around learner tasks.

The mission itself should remain visually dominant.

## 25. Mission Home

Mission Home is the permanent home for one mission.

The visual hierarchy should make:

## Start Mission / Continue Mission

the strongest action.

Keep:

- Mission Kit

- For Parents

clear and easy to find but subordinate.

Design relevant states for:

- before start;

- in progress;

- complete.

A completed mission should still feel accessible, not archived away or removed.

## 26. Mission Kit

Design Mission Kit resource presentation so resources are immediately scannable.

Support actions such as:

- View;

- Print;

- Download

where required.

Physical mission resources should feel like intentional parts of the learning experience, not like miscellaneous attachments.

Mission Kit and Mission Trail must remain visually distinct.

## 27. For Parents

Provide straightforward access to the Mission Note for Parents.

It should be:

- easy to find;

- clearly adult-facing;

- visually secondary to the child’s primary mission action.

Do not turn this into a separate parent dashboard.

## 28. Active Mission

The Active Mission environment should be the quietest part of the system.

## Design for:

- strong instruction hierarchy;

- obvious next action;

- restrained colour;

- comfortable reading;

- generous touch targets;

- minimal competing UI;

- enough space for concentration.

Do not decorate empty space simply because it exists.

Space is allowed to support focus.

The shared shell must be flexible enough to accommodate different mission types without forcing every mission into the same visual composition.

Do not design mission-specific screens until the relevant Mission Build Brief is approved, except where exploratory work is explicitly requested.

## 29. Screen ↔ physical handoffs

Hybrid handoffs are important design moments.

The child should be able to understand:

Where do I go? What do I do?

When do I come back?

Use hierarchy, spacing and clear transition language to make leaving the screen feel intentional.

The interface should orchestrate physical activity rather than duplicate it.

Do not create a digital version of an approved physical activity merely to make the interface feel fuller.

## 30. Mission Control

Design Mission Control as a reusable support component.

It should feel:

- available;

- calm;

- optional;

- supportive;

- secondary.

It should not look like:

- the answer;

- a reward;

- a rescue button;

- a hint ladder.

It should open and close without feeling like the child has entered another product.

Mission-specific wording comes from the relevant Mission Build Brief.

## 31. Mission Complete

Completion should feel satisfying and calm.

It should communicate:

- the mission is complete;

- the learner’s work still exists;

- they may return to My Missions;

- their Mission Trail remains theirs.

Avoid celebration mechanics that turn completion into scoring or reward.

The feeling is:

closure + evidence, not performance.

## 32. Mission Trail

Mission Trail is private selected evidence.

The design must distinguish between:

- evidence physically kept by the child;

- evidence actually stored digitally by the Academy.

Do not imply the Academy holds a digital copy of a physical artefact when it does not.

Digital Trail presentation should feel:

- private;

- reflective;

- evidence-led;

- non-competitive.

Do not introduce scores, rankings, public comparison or gallery assumptions.

## 33. Mission Board

Mission Board is a secondary Academy destination beneath Mission Home.

It is not part of the required mission path.

Contribution and moderation mechanics are not part of the current design scope.

Do not turn it into a social feed.

## 34. Mission-specific physical artefacts

Where the designer also produces mission-specific physical assets:

- work from the Child Mission;

- work from the applicable Child Mission Presentation Standard;

- work from the relevant Mission Build Brief;

- preserve the approved physical learning mechanic.

The physical artefact should align visually with WLA without allowing screen design to redefine how the mission works.

Physical and digital design should feel related, but they do not need to imitate each other.

Likely components include:

- My Missions cards;

- parent-note access;

- Mission Control;

- overlays;

## 36. Interaction and system states

Do not hand development static happy-path screens only.

Design meaningful states.

## Navigation

- default;

- current;

- hover;

- focus;

- mobile open/closed.

## Buttons

- default;

- hover;

- focus;

- pressed;

- disabled where appropriate.

## Mission cards

- Not started;

- In progress;

- Complete;

- hover/focus where relevant.

## Forms and inputs

- default;

- focus;

- error;

- success;

- disabled where relevant.

## Mission responses

Where required:

- available;

- selected;

- confirmed;

- locked;

- revealed.

## Shared system states

Where relevant:

- loading;

- empty;

- error;

- unavailable/resource failed;

- interrupted/restoring state.

Do not leave the developer to invent these visually.

## 37. Responsive design

Design for:

- desktop;

- smartphone portrait;

- tablet portrait;

- tablet landscape.

The Academy must not depend on desktop use.

Responsive design should preserve:

- hierarchy;

- action order;

- readable measure;

- touch comfort;

- mission handoff clarity;

- interaction-state clarity.

Do not simply shrink desktop layouts.

Pay particular attention to:

- navigation;

- Mission Cards;

- profile selection;

- My Missions;

- Mission Home;

- Mission Kit;

- response controls;

- overlays;

- long instructions;

- Journal reading;

- completion states.

No core action should depend on hover.

Where mobile or tablet behaviour differs materially from desktop, annotate the intended

behaviour explicitly rather than leaving development to infer it.

## 38. Accessibility

Design for:

- sufficient contrast;

- visible focus;

- comfortable touch targets;

- readable type;

- text enlargement;

- keyboard use;

- reduced motion;

- non-colour state communication;

- meaningful reading order.

Avoid interfaces requiring:

- tiny drag targets;

- precise pointer interaction;

- hover-only explanation;

- subtle colour differences alone;

- decorative motion to communicate state.

## 39. Motion

Motion should clarify state or orientation.

Appropriate examples:

- restrained accordion opening;

- subtle panel transition;

- clear state change;

- minimal navigation transition.

## Avoid:

- confetti;

- bouncing;

- spinning;

- game-like reward motion;

- auto-advancing carousels;

- heavy parallax.

The interface should feel alive without becoming animated for its own sake.

## 40. What not to design yet

Unless separately approved, do not design:

- subscriptions;

- points;

- badges;

- streaks;

- rankings;

- leaderboards;

- social profiles;

- chat;

- notifications;

- My Missions search/filter;

- mission replay;

- public Mission Trail sharing;

- compulsory upload workflows;

- Mission Board contribution/moderation mechanics.

These are outside the current core design scope.

## 41. Working with the developer

Designer and developer should share one component/state language.

The designer should provide enough information that the developer does not have to infer:

- hierarchy;

- component behaviour;

- spacing relationships;

- responsive changes;

- interaction states;

- focus states;

- empty states;

- error states;

- transition behaviour where meaningful.

If a design creates a technical conflict:

- 1. understand the implementation constraint;

- 2. preserve the approved product behaviour;

- 3. identify the least disruptive visual solution;

- 4. flag any genuine product decision.

Do not silently rewrite architecture through interface design.

## DESIGN PRINCIPLE

## Understand what is already working. Carry it forward with discernment. Build one production-quality visual system. Let the missions supply the intrigue.

The public prototype already demonstrates much of the intended public-site character. The Website Master determines what the public experience contains. The Academy Architecture determines how the shared learner environment behaves. Mission Build Briefs determine what

is unique inside each mission.

The designer’s role is to bring those layers together into one WLA: clear, tactile, thoughtful,

capable and increasingly distinctive — without allowing the interface to become the activity.
